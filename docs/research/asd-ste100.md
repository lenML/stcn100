# ASD-STE100 Issue 9 调研

> 文档状态：调研稿  
> 核对日期：2026-10-04  
> 研究对象：ASD-STE100 Simplified Technical English, Issue 9, 2025-01-15  
> 适用项目：stcn100 中文技术写作规范与 CLI lint 工具

## 1. 结论摘要

1. ASD-STE100 是面向技术文档的受控自然语言，由写作规则和受控词典两部分组成。Issue 9 标题为 「Standard for technical documentation」，包含 9 个规则章节，共 53 条写作规则。[1][2][4]
2. Issue 9 官方词典收录约 875 个批准词和 1274 个未批准词。词典不是完整自然语言词表，而是受控词汇、批准含义和替代建议的组合。[4]
3. STE 不封闭技术术语。写作者可以在公司、行业或学科批准的术语库中使用技术名词和技术动词，但必须满足分类、词性、含义、命名一致性和使用场景要求。[4]
4. 最具机械检测价值的约束包括句长、段落句数、分号、复杂助动词结构、被动语态候选、`-ing` 形式、超长名词簇、缩写和计数规则。[4][5]
5. 最难机械判定的是语义和语用边界，包括批准含义是否吻合、技术术语是否属于当前领域、两个动作是否同时发生、注释是否暗含指令、段落是否只有一个主题、风险等级是否准确、改写是否保留原意。[4][5]
6. 官方明确表示检查工具不能替代写作者或标准本身。工具可以提示不符项，但不能可靠地把普通文本自动转换成合规 STE，也不能保证文本语义正确。[5]
7. 对 stcn100 最重要的启示不是逐条翻译英文语法，而是抽象出可控维度：上下文分类、句法与段落约束、术语库、可检测等级、人工复核门禁和场景预设。

### 4.1 第 1 节：Words

核心规则类别：

- 只能使用受控词典批准词、技术名词和技术动词。
- 批准词必须按指定词性和批准含义使用。
- 动词和形容词只能使用已批准形式。
- 技术名词和技术动词必须来自公司、行业或学科批准术语。
- 技术名词必须短、易理解，不得使用地区词、俚语和行业黑话。
- 同一对象必须使用同一技术名词。
- 技术名词不得随意当动词，技术动词不得随意当名词。
- 默认使用美式英语拼写，除非其他正式规范另有要求。

机械边界：词典命中、词性标注、词形变位和禁用词替换可以自动提示。但「这个词在此处是否使用了批准含义」「这个技术术语是否属于当前学科」「这个新术语是否足够清晰」都需要语义或术语治理。

### 4.2 第 2 节：Multi-word nouns

核心约束：

- 普通多词名词最多 3 个词。
- 超过 3 词的技术名词必须按照正式术语写全，再在合适位置定义短形式或批准缩写。
- 可以使用介词拆分名词簇，降低修饰关系歧义。
- 可以有限使用连字符把相关词组成一个理解单元，但不能靠连字符掩盖超过 3 词的名词簇。

机械边界：一旦分词、词性、技术术语边界和豁免范围确定，`名词簇长度 > 3` 可以自动检测。是否属于正式技术名词、是否应缩写、缩写是否已定义、连字符是否改变含义，需要术语库和人工判断。

### 4.3 第 3 节：Verbs

核心约束见「核心约束」章节。该节是 CLI 能获得较高收益的区域，因为复杂时态、助动词、被动语态和 `-ing` 形式都有可解析模式。

### 4.4 第 4 节：Sentences

核心约束：

- 句子应短且清楚。
- 不得通过省略主语、动词、名词、冠词或使用缩写形式来缩短句子。
- 复杂项目或动作可使用垂直列表。
- 使用连接词或连接短语表达句子间关系。
- 在适用时，名词或名词短语前应使用冠词或指示形容词。

机械边界：缩写形式、列表符号、冒号和冠词缺失可以部分自动检测。句子是否真的清楚、冠词缺失是否造成歧义、连接关系是否符合逻辑，需要语义判断。

### 4.5 第 5 节：Procedural writing

核心约束：

- 操作句每句最多 20 词。
- 每个句子通常只写一个指令，除非两个或多个动作同时发生。
- 一个步骤可以含多个句子，当动作同时发生或结果紧接动作时需要保留在同一逻辑步骤。
- 操作指令使用祈使形式。
- 条件必须先于命令，并用逗号与命令分开。
- 注释只提供信息，不给指令、限制、公差或结果要求。

机械边界：20 词上限、注释句长、祈使形式候选和条件前置结构可以自动检查。「是否为同一个动作」「动作是否同时发生」「结果是否紧接动作」「注释是否事实上构成安全指令」需要语义判断。

### 4.6 第 6 节：Descriptive writing

核心约束：

- 信息逐步展开，避免一句话塞入多个主题。
- 关键词和关键短语保持稳定，形成逻辑结构。
- 说明句每句最多 25 词。
- 段落用于组织一个主题下的内容。
- 每个段落只允许一个主题，段首通常为主题句。
- 每个段落最多 6 句。

机械边界：25 词上限和 6 句上限可直接计算。主题句识别、单主题判断、信息递进、关键词是否真的连接主题，需要语义分析。

### 4.7 第 7 节：Safety instructions

核心约束：

- 使用 warning、caution 或等效风险标签标识风险等级。
- 安全指令以清楚的命令或条件开头。
- 应说明违反指令后的风险或后果。
- warning 用于人身伤害或死亡风险，caution 用于设备或对象损坏风险。其他行业可以替换标签词，但仍需满足相同内容要求。

机械边界：标题词、命令或条件位置、风险说明是否存在可以模式化检测。风险等级、后果真实性、标签是否与风险匹配必须人工或由受控语义审核完成。

### 4.8 第 8 节：Punctuation and word count

核心约束：

- 不允许使用分号。
- 连字符用于连接直接相关的词。
- 括号有明确允许用途，包括引用、编号、缩写、说明、单复数或替代内容。
- 垂直列表中的冒号具有句末作用，冒号前文本和每个列表项分别受句长限制。
- 括号内容在主句中计为一个词，但括号内部文本另算一个句子。
- 数字、数字加单位、缩写、字母数字标识、引文、标题、标签和专有名词各自计为一个词。
- 段落或步骤编号不计词。
- 连字符连接词计为一个词。

机械边界：这是最适合 linter 的章节，但计数必须是「结构解析后的计数」，不能简单按空格或字符切割。代码块、行内代码、引文、标题、表格和编号系统必须有排除规则。

### 4.9 第 9 节：Writing practices

核心约束：

- 逐词替换会改变含义或词性时，必须改变句子结构。
- 批准词也必须按正确含义和正确词性使用。
- 两个词组合后形成新语义时，应避免使用该短语动词；除非项目明确批准该短语。
- 同类信息、同类操作和同一对象应使用一致术语与一致句式。

另外，GR-1 到 GR-8 是 general recommendations，不是 53 条规则本身。它们覆盖 `that`、`with`、代词、`this`、假朋友、拉丁缩写、包容性语言和所有格。适合作为可选 lint 规则包，不应在合规报告中伪装成核心规则违规。

## 5. 核心约束

### 5.1 句子长度与计数

| 文本类型 | 硬上限或结构 | 关键条件 |
| --- | --- | --- |
| 操作句 | 每句最多 20 词 | warning、caution 和其他安全指令也适用 |
| 说明句 | 每句最多 25 词 | 注释按说明文处理 |
| 注释 | 每句最多 25 词 | 注释只能给信息 |
| 段落 | 最多 6 句 | 面向说明文段落 |
| 垂直列表 | 冒号等价句末 | 冒号前和每个列表项分别计数 |
| 括号 | 主句内计 1 词 | 括号内部另算句子 |
| 步骤编号 | 不计词 | 段落号、步骤号属于文档编号系统 |
| 数字加单位 | 计 1 词 | 例如数值加单位视为一个计数单元 |
| 缩写和标识 | 各计 1 词 | 字母数字标识、缩写、引文、标题、标签、专有名词 |
| 连字符词 | 计 1 词 | 但不得用它制造不可读的任意长复合词 |

实现提示：中文版不能直接复用「英语单词空格计数」。需要把长度建模成可配置指标，例如汉字数、词法词数、分句数、谓词数或阅读负荷。英文 STE 计数规则可以作为结构化计数的测试基准，而不是中文规范本身。

### 5.2 动词形式、时态和语态

| 约束 | 机械候选模式 | 语义或例外 |
| --- | --- | --- |
| 只用批准动词形式 | 词典查表 | 词义语境和术语库 |
| 允许不定式、祈使、一般现在、一般过去、一般将来 | 形态和依存分析 | 句子类型识别 |
| 过去分词只作形容词 | `be/become/stay + participle`、名词前分词 | 需要区分被动和状态形容词 |
| 禁止复杂助动词结构 | `have/has/had + participle`、`be + participle`、情态动词复杂结构 | 部分情态结构属于批准用法 |
| `-ing` 只用于技术名词或技术名词修饰语 | POS 和依存分析 | 需区分动名词、现在进行、标题词、功能修饰语 |
| 使用主动语态 | `be/get + past participle`，存在 `by` agent | 说明文在施事未知时允许被动 |
| 动作用批准动词表达 | 名词化检测、轻动词结构检测 | 批准动词是否存在、改写是否等价 |

高风险点：被动语态是「候选检测」而不是纯错误检测。官方明确允许说明文在施事未知时使用被动。因此 linter 应报告 `passive-candidate`，而不是直接判死。

### 5.3 名词簇、术语与一致性

| 约束 | 可否机械检测 | 必要条件 |
| --- | --- | --- |
| 普通多词名词不超过 3 词 | 高 | 分词、词性、技术术语边界、代码和引文排除 |
| 长技术名词首次写全 | 中 | 术语库、首次出现位置、缩写定义 |
| 同一对象使用同一技术名词 | 中到高 | 实体识别、别名表、同指判断 |
| 技术名词不得当动词 | 中 | 词性标注和技术词库 |
| 技术动词不得当名词 | 中 | 词性标注和技术词库 |
| 不使用地区词、俚语、黑话 | 低 | 区域语言资源、领域专家审核 |
| 技术术语必须属于批准领域 | 低 | 分领域术语库和术语治理流程 |
| 使用美式拼写 | 高 | 字典映射，但引文和正式标识应豁免 |

实现提示：术语一致性是通用技术写作最容易获得高价值的部分，但必须区分「同一概念的批准术语」与「因缩写、单复数、产品正式名称导致的允许变体」。不要把字面相似自动判为同义或冲突。

### 5.4 操作步骤、条件、注释和安全

| 约束 | 机械可做 | 人工或语义必须做 |
| --- | --- | --- |
| 每句最多 20 词 | 是 | 句子切分和豁免区 |
| 每句一个指令 | 候选提示 | 判断多个动作是否同时发生 |
| 操作使用祈使句 | 句法候选 | 判断当前块是否真的是操作步骤 |
| 条件先于命令 | 是，识别条件从句和主句 | 判断条件含义和逗号位置影响 |
| 一个步骤只能一动作或紧邻结果 | 弱提示 | 判断动作与结果的因果关系 |
| 注释不含指令 | 祈使句候选 | 注释是否隐含要求、限制或风险 |
| 注释不承载公差和结果 | 数值和情态模式提示 | 判断数值是否属于步骤结果 |
| warning 或 caution 标签 | 词面检测 | 风险等级是否匹配 |
| 先命令后解释后果 | 结构提示 | 后果是否真实、具体、完整 |

### 5.5 段落、结构和风格

| 约束 | 机械可做 | 人工或语义必须做 |
| --- | --- | --- |
| 每段最多 6 句 | 是 | 引用、列表和表格的边界处理 |
| 每段一个主题 | 弱提示 | 主题建模和同指关系 |
| 段首主题句 | 弱提示 | 判断真正的段落主题 |
| 关键词稳定 | 术语库比对 | 判断是否指同一概念 |
| 信息逐步展开 | 基本不可靠 | 信息增量、依赖关系和读者负荷 |
| 术语和句式一致 | 模板和聚类提示 | 上下文相同性和含义等价性 |
| 不用短语动词 | 列表和依存候选 | 组合是否产生新语义、是否获批准 |

## 6. 机械检测与语义判断边界

建议把每条检查拆成四级，不要只标记「合规」和「不合规」。

| 等级 | 名称 | 判定方式 | 输出策略 | 典型规则 |
| --- | --- | --- | --- | --- |
| M0 | 机械确定 | 规则不依赖未提供的语义上下文，且作用域明确 | 可直接报 error，仍允许 ignore 注释 | 分号、句数上限、数字段落编号计数、连字符计数 |
| M1 | 解析高置信 | 句法或形态模式可确定候选，但存在上下文例外 | 报 warning，可附证据和修复方向 | 被动语态、复杂助动词、`-ing`、祈使句、名词簇超限 |
| M2 | 词典或术语库依赖 | 判定依赖受控词典、术语库、批准缩写或产品词表 | 报 term issue，要求术语库或负责人确认 | 批准词、词性、词形、术语一致性、拼写 |
| M3 | 语义或治理判断 | 需要理解意图、读者、风险、同指或文档目标 | 报 review item，不能单独阻断发布或自动改文 | 批准含义、主题、动作同时性、注释边界、风险等级、改写等价性 |

### 6.1 可直接机械检测的内容

前提是已经完成块分类和排除区识别。

- 句长超过操作文 20 词或说明文 25 词。
- 段落超过 6 句。
- 明确出现分号。
- 文本块内出现禁止的缩写形式，英文场景例如 `don't`、`isn't`。
- 列表项没有按配置的标记和结尾标点组织。
- 括号内文本是否按一个词参与主句计数。
- 数字加单位、缩写、引文、标题、标签、专有名词和字母数字标识的计数。
- 连字符连接词是否按一个词计数。
- 配置化禁用词或未批准词直接出现。
- 正式术语库中定义的两个不同术语在同一对象上下文中混用。

即使 M0 也需要 parser，因为分号也会出现在代码、引文、URL、表格公式或文本块的非正文区域。

### 6.2 解析器可高置信提示的内容

- 被动语态候选：助动词加过去分词、`by + agent`。
- 完成时或进行时候选：`have/has/had + past participle`、`be + -ing`。
- 复杂情态结构候选：`can be adjusted`、`must be done`、`is to be installed` 等。
- `-ing` 形式用于谓语、修饰语、技术名词或标题的区分。
- 超过配置长度的名词簇候选。
- 操作块中的非祈使句候选。
- 条件从句是否位于命令之前。
- 注释块中的祈使句候选。
- 短语动词候选：动词加介词或副词。
- 缺失冠词候选。

这些候选仍需要豁免规则：

- 过去分词属于已批准的状态形容词。
- 被动语态出现在未写明施事的说明文中。
- `-ing` 词属于已批准技术名词或固定技术名词的一部分。

### 6.3 必须依赖词典和术语库的内容

- 一个词是否是批准词。
- 批准词是否按指定词性使用。
- 词形是否超出批准变位。
- 词义是否等于批准含义。
- 一个未批准词是否可以作为当前领域技术名词或技术动词。
- 一个技术术语是否来自公司、行业或学科批准术语。
- 缩写是否已在首次出现位置定义。
- 同一对象是否使用了批准术语。
- 拼写是否符合批准词表或正式指令。

这部分可以完全本地化，但前提是合法获取或自行建立词典和术语数据。若无法使用官方词典数据，应让用户配置自有词表、批准术语和替代映射。不要把官方受版权保护词典直接打包进项目。

### 6.4 主要依赖语义判断的内容

- 「批准含义」在当前语境中是否真正成立。
- 技术语境是否把普通词用作技术术语。
- 两个动作是否同时发生。
- 第二句是否只是同一步骤的紧接结果。
- 注释究竟是信息，还是伪装成信息的安全要求。
- 一个段落是否只有一个主题。
- 第一句是否为真正的主题句。
- 关键词复现是否指向同一概念。
- 信息是否逐步展开而非一次堆叠。
- 被动语态是否因为施事未知而无替代主动句。
- warning 与 caution 的风险等级是否准确。
- 词级替换是否保持技术含义。
- 风格变化是否只影响表达，还是实际改变对象、动作或结果。

## 7. 对 stcn100 的设计启示

### 7.1 不要把 STE 机械翻译成中文规则

中文没有与英语完全对应的时态屈折、冠词、空格分词和被动形态。直接移植会造成误报和错误建议。应继承其控制维度：

- 句长和阅读负荷。
- 操作与说明的文本类型区分。
- 行动者、动作、对象、条件、结果显式化。
- 术语、词性、含义和拼写的一致性。
- 步骤顺序、单动作原则和条件前置。
- 段落主题、信息递增和句间逻辑。
- 安全标签、风险等级和后果说明。
- 自动检测、术语审查和人工复核的分层。

### 7.2 规则元数据建议

每条规则至少需要这些字段：

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定规则标识，例如 `stcn.procedure.max-clauses` |
| `section` | 基础规则、coding 预设、技术文档预设等 |
| `scope` | procedure、description、note、safety、heading、code、quote |
| `level` | error、warning、info、review |
| `detectability` | mechanical、parser、lexicon、semantic |
| `autofix` | none、safe、suggestion |
| `requires` | parser、glossary、terminology database、semantic reviewer |
| `evidence` | 违规片段、计数、命中模式、对应术语 |
| `exemption` | code span、URL、引用、正式名称、表格、标题等 |

### 7.3 Lint 流水线建议

```text
输入文本
  -> 文档与代码块解析
  -> 文本块分类（操作/说明/注释/安全/标题/引文/代码）
  -> 中文分句与结构标记
  -> 机械规则检查
  -> 句法和形态规则检查
  -> 术语库与一致性检查
  -> 语义复核规则
  -> 输出分等级诊断
  -> 安全自动修复或建议式改写
```

### 7.4 自动修复边界

适合自动修复或自动建议的内容：

- 确定性标点规范。
- 可安全识别的重复空格、统一术语大小写和标点。
- 超长句的位置提示和拆分点候选。
- 未批准术语到自有术语库批准术语的映射。
- 同一对象术语变体的统一建议。

不适合自动修复的内容：

- 被动改主动。
- 将一句拆成多个操作步骤。
- 把注释改写成指令。
- 重写句义以替换未批准词。
- 收紧或放宽安全风险。
- 判断段落主题。
- 在多个同义词之间选择批准术语。

### 7.5 场景预设建议

基础中文技术写作预设：

- 控制句长和段落复杂度。
- 操作步骤使用明确动作。
- 条件和结果前置或按顺序显式表达。
- 同一概念同一术语。
- 禁止歧义代词和无先行词指代。
- 注释、提示、警告和步骤分离。

Coding 文档预设：

- 代码块、行内代码、命令、路径、日志、URL、API 标识符全部豁免。
- 注释、提交信息、技术说明、README 和用户文档可分别配置。
- 检查「一个步骤一个主要动作」、条件优先、术语一致和危险操作标识。
- 对 shell 命令的风险标签、破坏性操作和回滚说明建立专属规则。

通用技术文档预设：

- 操作步骤和说明文字分开。
- 警告、注意和普通提示分级。
- 术语库、缩写表和产品名作为项目配置。
- 段落主题、同义词混用和句式模板作为跨文档检查。
- 输出 SARIF 或 JSON，便于 IDE、CI 和编辑器集成。

## 8. 优先开发顺序

1. 文档解析和受保护区域：代码、引用、URL、表格、标题、编号。
2. 文本块分类：procedure、description、note、safety、heading、quote、code。
3. 机械规则：句长、段长、分号、列表结构、计数规则。
4. 术语库：批准词、技术名词、技术动词、缩写、拼写和替代映射。
5. 解析规则：被动候选、复杂助动词、`-ing`、名词簇、祈使句和条件顺序。
6. 语义复核：主题、动作同时性、注释边界、风险等级、改写等价性。
7. 场景插件：coding、技术文档、通用中文写作。
8. 报告与 CI：JSON、SARIF、编辑器诊断、基线抑制和规则进度。

## 9. 待决策问题

- 中文规则的长度单位采用汉字数、词数、分句数，还是组合评分。
- 中文操作步骤是否强制每个句子一个动作，还是允许同主语连续动作。
- 中文警告标签采用固定词表，还是允许项目自定义并做映射。
- 官方词典不进入仓库时，内置规则和用户术语库如何分层。
- 语义规则默认由本地模型、远程模型还是人工审核处理。
- coding 预设中哪些符号区和标识符必须无条件豁免。
- 规则等级是否允许按项目、目录、文件类型和块类型覆盖。
- 是否提供自动修复，还是只提供诊断和改写建议。
